# CLAUDE.md

Raspberry Pi three-factor-auth vault game (RFID card, Wordle-style PIN, face recognition). See README.md for the overview.

## Environment
- Code runs on a Raspberry Pi 4 (Raspberry Pi OS Bookworm, KDE, Python 3.11) from a clone of the repo in the user's home directory (`~/Can-you-break-the-bank`). Don't hard-code that path anywhere: `app_config.py` defaults `base_dir` to the folder it lives in, and the paths to videos, images and `includes/` are resolved against it (overridable in the `[paths]` section of the config file - see Configuration). On the Pi, pip packages live in `.venv` in the clone (created with `--system-site-packages`, see SETUP.md), so scripts are run as `.venv/bin/python <script>` and subprocesses use `sys.executable`, not `python`. PyQt6 and OpenCV come from apt, not pip: don't pip-install OpenCV (it overwrites the apt copy's files and breaks `import cv2`).
- Development happens on Windows, where the hardware modules (`RPi.GPIO`, `picamera2`, `neopixel_spi`, `board`, `smbus`) can't be imported. The app is built so it still runs there: `[hardware] backend = auto` falls back to simulated hardware, a simulated card reader and face engine, a synthetic camera and an in-memory store (frame 3 says "SIMULATED ..." when it does). That fallback only applies when the Pi hardware isn't there: once `RealHardware` starts, `main()` forces the backend to `real`, so on a Pi a missing Redis (retried for 30 seconds, as it may still be starting at boot), camera or `face_recognition` is an error and never a silent stand-in. A venv with PyQt6, `opencv-python-headless` and numpy is enough (`python vault_app.py --windowed`; type card numbers into the strip at the bottom of the window). Set `[camera] type = webcam` and `webcam_device = 0` to use a real webcam. Run the tests with `python -m unittest` from the repo root. Don't run the Pi-only scripts (`read_rfid.py`, `redis-sync.py` and so on) on Windows, and never `delete_all_redis_keys.py`.
- Each Pi drives an external HDMI screen (not a touchscreen, but it has a mouse and keyboard) at anything up to 4K, so the layout is proportional to the window size, not fixed pixels.
- No build step or package manifest. `Images/` is tracked in git (all copyright material has been removed). `includes/` is git-ignored (mixed licensing, deal with later) - don't add or commit its contents. It holds the SB Components RFID HAT files: `oled_091.py` (the smbus2 variant, provided by SB Components - don't modify it), `SB.png` and `Fonts/`. `oled_091.py` loads its font from `Fonts/` next to itself, so `Fonts/` must stay inside `includes/`. These files are only relevant if the SB Components HAT is the one in use; only PiFace2 has the OLED, and the app carries on without it elsewhere.

## Deployment modes
The activity runs in one of two ways, always with the same app (`vault_app.py`), which switches between vault and enrol modes on screen:
- **Single Pi:** alternate between enrol mode and vault mode on the same Pi, using its local Redis.
- **Two Pis:** normally enrolment runs on **PiFace1** (`192.168.8.152`) and the game on **PiFace2** (`192.168.8.153`). `redis-sync.py` replicates Redis between them and must stay **bi-directional**, so either Pi can do either job - e.g. PiFace1 can run the game when the enrolment queue is short but the game queue is long.

The mode is set per Pi by the `[redis]` section of the config file. A `remote_host` means dual node mode and should be the *other* Pi's IP, so the two Pis have different configs and no IP addresses are hard-coded in the scripts. No `remote_host` (or no config file) means single node mode.

## Configuration
Settings live in `~/.config/can-you-break-the-bank/can-you-break-the-bank.cfg` (template: `can-you-break-the-bank.cfg.example`), read by `app_config.py` (`load_config()` returns a flat dict). Every option is optional and defaults to the original hard-coded value. Sections: `[app]`, `[redis]`, `[camera]`, `[enrolment]`, `[pin]`, `[face_recognition]`, `[hardware]`, `[paths]`. `[redis] password` (optional, the same on both Pis, used for the local and remote Redis) is needed in dual node mode: Redis 7+ refuses other machines while protected mode is on and no password is set, whatever `bind` says (SETUP.md section 5). `delete_all_redis_keys.py` lets the `*_REDIS_PASS` env vars override it. `[pin] pin_length` is shared by the PIN game and the enrolment checks. `[app] admin_pin` (optional) guards switching mode and exiting. When adding a setting, add it to `app_config.py` (with its default) and to the example file rather than hard-coding it in a script. Unknown options are ignored, so an old config file still loads.

`[camera] type` is `picamera` (Pi camera via Picamera2, imported only when used) or `webcam` (USB webcam). The app opens the camera with `camera_worker.open_app_camera(config)`, which uses `open_camera(config)` from `camera_setup.py` (the Pi camera uses the preview configuration with the configured frame rate). Both camera types provide `capture_array()`/`close()` and give BGR frames, so the colour handling is the same. Don't duplicate the camera setup.

## Architecture
`vault_app.py` is the application: one PyQt6 window in three frames, run as `.venv/bin/python vault_app.py` (`--mode vault|enrol`, `--windowed`). Frame 1 (left 70%) is the vault image, the access granted/denied banner and the granted/denied videos (played in-frame with sound, fitted not cropped; the vault image is cropped to fill). Frame 2 (top right) is the step chips, instructions and the PIN game or the enrolment form. Frame 3 (bottom right) is the camera feed and recognition feedback; it takes more of the height while a face is captured. While a face is being enrolled the camera moves to frame 1 as a large live view (`StagePane.show_live`) and frame 3 lists the facial features found and their coordinates (`CameraPane.show_features`). `MainWindow` is a small state machine (idle, pin, face, result, and the enrol states); `STYLE` and `resizeEvent` scale all fonts and padding from the window height.

- Factor 1: `rfid.py` reads the serial port on its own thread (`/dev/ttyS0` by default). The reader only delivers a card once armed (`arm()`), and calls back on its own thread, so `MainWindow` hands the card over with a Qt signal. A simulated reader stands in when the hardware is simulated.
- Factor 2: `pin_game.py` is the Wordle-style game, UI-free. The `PinGame` timer and guess limit come from `[pin]`; a correct guess on the last allowed attempt still passes. `panes.PinGameWidget` shows it in frame 2.
- Factor 3: `face.py` holds the decision rules (`FaceVerifier`), `camera_worker.py` the threads, `face_engine.py` the detection. The `timer_seconds` timer starts on the first detected face (gives up after `face_wait_seconds` with no face); a vote passes early when `vote_required` of the last `vote_window` recognition passes matched (distance <= `match_threshold`), then the live video holds for `pass_hold_seconds` with a "PASSED" banner. The vote is 1:1 against the scanned card's enrolled encoding, so other faces in frame never affect it; boxes are green (this card), amber (another enrolled card) or red (not recognised). Detection/encoding runs on every `recognise_every_n`th frame in a separate thread (frames offered while it's busy are dropped), and each pass is one vote. Frames are converted BGR to RGB before encoding (the camera's "RGB888" frames are BGR in memory); keep enrolment and verification in step or distances rise. Every pass is appended to `face_log.csv` (path in the config, git-ignored) for tuning the `[face_recognition]` settings.
- Enrolment: scan a card, enter a name and a PIN twice, then `training_images` (10 by default) single-face encodings are averaged and saved automatically with `store.CardStore.save`, as a hash at `card:<id>` (`name`, `pin`, pickled `encoding`) in local Redis. Capture has no time limit: it goes on until the images are taken or Exit is clicked (Exit during capture cancels it, saving nothing, with no admin PIN; anywhere else it still quits the app). While capturing, `RecognitionWorker` also asks the engine for the facial features (`detect(..., landmarks=True)`), `CameraWorker` draws them on the frame as red lines with the green face box and a "Training image n/N captured" banner, and frame 3 lists them, as the old enrolment window did. An existing card is only replaced when the new details are saved.
- `store.py`: the Redis `card:<id>` load/save (and `MemoryRedis`, the in-memory stand-in used by the tests and by development without Redis). Redis scripts stay separate from the app.
- `hardware.py`: the buzzer, beacon, NeoPixel ring (including the attract-mode chase) and the OLED behind one interface, with `RealHardware` and `SimulatedHardware` (`[hardware] backend = auto|real|simulated`). Nothing is initialised at import time; `create_hardware(config)` does it. The OLED is optional.
- `panes.py`: the three frames and their widgets. They show what they're told and emit signals; they know nothing about hardware, Redis or recognition.
- `app_config.py`: shared config loader (see Configuration), including the single/dual node mode. Used by the app, `redis-sync.py`, `delete_all_redis_keys.py`, `show_all_keys.py` and `read_rfid.py`. It must be deployed alongside them, as must `camera_setup.py` and the app's modules.
- `redis-sync.py` replicates the local Redis to a second Pi via keyspace events. In single node mode it logs and exits 0 (`redis-sync.service` uses `Restart=on-failure` so systemd leaves it stopped). `delete_all_redis_keys.py` and `show_all_keys.py` act on the local Redis, plus the remote one in dual node mode; the delete script ignores `--stop-service`/`--start-service` in single node mode. `reset_all_redis.sh` stops `redis-sync.service`, runs the delete script from its own directory, then restarts the service.
- `redis.service` is a reference copy of the Redis unit. `redis-sync.service.template` is the template for the sync unit: it has `@USER@` and `@INSTALL_DIR@` placeholders because systemd units need absolute paths and can't use `~`; SETUP.md installs it with a `sed` command to `/etc/systemd/system/redis-sync.service` (run `sudo systemctl daemon-reload` after changing it). The unit sets no remote host - that comes from each Pi's config file, and a Pi with no config file silently runs in single node mode (sync stops), so create the config on every Pi.
- `run_vault.sh` is the kiosk wrapper: it runs `vault_app.py` (extra arguments are passed on), restarts it 3 seconds after a non-zero exit, stops on exit status 0 (the Exit button) and logs to `vault_app.log` (git-ignored, emptied above 1 MB). `can-you-break-the-bank.desktop.template` is the XDG autostart entry for it, with an `@INSTALL_DIR@` placeholder (the `Exec` line needs an absolute path) that SETUP.md section 10 fills in with `sed` into `~/.config/autostart/`. Autologin and disabling screen blanking are manual steps in that section. Keep `run_vault.sh` executable (`git update-index --chmod=+x`) and with LF line endings.
- `read_rfid.py` is a standalone tool for reading card IDs; `retrieve_redis.py` is a demo only.

## Conventions
- Match the surrounding style: plain Python, 4-space indentation, short comments that say why. Keep logic that can be tested out of the Qt code (as `pin_game.py`, `face.py`, `store.py` and `rfid.py` are) and add `unittest` tests in `tests/` for it. Settings come from the config file via `app_config.py` (don't hard-code IPs, pins, paths or tuning values); `delete_all_redis_keys.py` still takes the Redis DB number and password from env vars.
- Anything that talks to the hardware goes through `hardware.py`, so the app keeps working in simulation. Never block the Qt thread: camera, recognition and card reading are on their own threads and reach the UI through signals.
- The remote Redis IP differs between the two Pis' config files because each is configured for the *other* Pi (see Deployment modes). `redis-sync.py` runs as a systemd service (`redis-sync.service`) on **both** Pis, each pointing at the other Pi, which is what makes the sync bi-directional. Don't change the sync design in a way that makes it one-directional.
- `delete_all_redis_keys.py` is destructive (flushes the local Redis and, in dual node mode, the remote one). Never run it.

## Known issues (not yet fixed)
- Two GStreamer `CRITICAL` assertions (`GST_IS_ELEMENT (element)` and `gst_alsa_device_new: assertion 'caps' failed`) print to stderr when the app starts, from Qt Multimedia probing the audio devices (probably the HDMI port with no screen on it). They don't affect the video or its sound. Pinning the audio output to the HDMI port in use would hide them.

## Verified on a Pi
The single-window app (`vault_app.py`) has been installed and tested as working on PiFace2 (Pi 4, Pi HQ camera, Bookworm, with the OLED display) and on PiFace1. Video with sound plays in frame 1. The kiosk autostart (`run_vault.sh` and the autostart entry, SETUP.md section 10) has not been tried on a Pi; the wrapper's restart and exit handling was tested with a stand-in program. Dual node mode with the Redis password (`[redis] password`, `bind` to the Pi's LAN address, protected mode on) works between the two Pis, `redis-sync` runs on both, and after a reboot of each Pi `redis-server` and `redis-sync` both came up by themselves. A card enrolled in the new app appeared on the other Pi, in both directions (PiFace1 to PiFace2 and PiFace2 to PiFace1). The enrolment live view (features drawn on the large view in frame 1, the feature list in frame 3) has been tried on PiFace2 with a real face: the lines follow the face smoothly and the list updates, Exit during capture cancels without saving, and capture has no time limit. Single node mode and config options other than the defaults have also been tested on a Pi. The one thing still unchecked is the kiosk autostart (above): check it before relying on it, and update this section when done.
